# Removal and garbage collection

[README](../README.md) · [Commands](commands.md) · [JSON](json.md)

Retire workspaces with explicit selectors. See [command options](commands.md) for the full syntax.

## Local preservation

Remove runs trusted `pre-remove` hooks before deleting the checkout and rechecks the target after hooks. A branch is preserved when its commits are integrated into its base (normal merge, or squash/rebase proven by exact tree-entry transitions) or its tip exactly matches its own upstream. With no recorded base, retirement checks the repository default base. For local proof, the base or upstream must resolve to an independent ref in the common Git directory, including custom fetch namespaces. A symbolic alias to the retiring branch, detached HEAD, or a bare commit ID does not establish preservation. Preserved branches are deleted; other branches stay with warning `branch_kept_unpreserved` and `branchKeptReason: "unpreserved"`. `--keep-branch` always keeps the branch; `--delete-unpreserved-branch` explicitly permits deleting unpreserved history.

## GitHub merged-PR evidence

After local preservation checks fail, remove and gc can use GitHub evidence for a named branch. A recorded PR (`set --pr` or `create --pr`) must be `MERGED`, and its `headRefOid` must equal the local tip or contain it as an ancestor. Ancestry is checked only when that PR commit already exists locally; nothing is fetched. Partial clones (`extensions.partialClone` configured or any remote with `promisor=true`) require an exact tip match and skip PR object and ancestry probes on every Git version. A recorded URL is passed to `gh` and must match the checkout repository resolved by `gh repo view`; number-only links use that repository. Unlinked branches use one `gh pr list --head BRANCH --state merged --limit 2` query and require exactly one result with the same head name and exact tip ID; ancestry is never used. Repository identity is resolved once per command. Missing or unauthenticated `gh`, failed queries, invalid JSON, ambiguous identities, and timeouts keep the existing local verdict. Each gh call has a 10-second deadline (shorten it with positive `RABI_GH_TIMEOUT_MS`); authentication prompts are disabled and non-interactive stdin is `/dev/null`. Remote responses, including failures, are cached for the command, while local tips and ancestry are rechecked after hooks. JSON items add `preservationReason`: `merged_pr` for GitHub proof, `local` for remove's local proof, otherwise null or absent. Text details identify merged-PR proof. These rules also apply to plans. Known limit: repository identity is compared as `https://HOST/OWNER/REPO` without a port, so GitHub Enterprise hosts served over plain HTTP or on a non-default port never prove a merged PR; those branches are kept (use `git branch -d` after checking).

## Dirty work and explicit permissions

Modified or staged tracked files (including submodule changes) and non-ignored untracked files require `--discard-changes` (otherwise exit 4 `dirty`). Unpreserved detached commits require `--delete-unpreserved-branch` (otherwise exit 4 `unpreserved`). The two permissions are independent. The primary checkout always exits 4 `primary`. `--dry-run` runs no hooks and changes no files, refs, or records; its items have `removed: false`, `wouldRemove`, and `wouldDeleteBranch`, with `plan: true`.

For remove (including `--dry-run`) and gc (plan and `--apply`), dirty uses the same rule as list/show. Ignored files do not count as dirty and are deleted with the workspace without a warning or `--discard-changes`. Known limitation: nested Git repositories inside ignored directories (for example, `vendor/x/.git` under ignored `vendor/`) are also deleted with the workspace.

Even when clean, workspaces with populated submodules or retained submodule data are refused during remove preflight (exit 4 `dirty`, including `--dry-run`) and skipped by gc (plan and `--apply`) with a `rabi remove NAME --discard-changes` hint; review the submodule contents, including unpushed commits, before using that permission.

## Preflight and results

`remove --json` returns the shared schema 2 envelope. `data.items` contains `workspace`, `removed`, `branchDeleted`, `branchKeptReason`, `preservationReason`, `detail`, `alreadyGone`, and `error`. Dry runs add `data.plan`; their items also include `wouldRemove` and `wouldDeleteBranch`.

Per-item errors are structured `{code,message}` objects. A selector with neither a metadata record nor a matching Git worktree exits 3 `not_found`, including with `--dry-run`. Every selector is checked first: one unknown target prevents all hooks and removal, and text output lists every unknown selector. Select by name, `.`, `pr:N`, `issue:N`, PR/issue URL, or an absolute path or path starting with `./` or `../`.

`alreadyGone: true` requires evidence of the workspace. A missing directory with a record, a Git registration inside the workspace directory, or both succeeds with exit 0; only stale records and registrations are removed, without hooks or branch deletion. If a record and files remain but the Git registration is gone, remove acknowledges it with `alreadyGone: true` and leaves the files, record, and branch untouched. A branch alone or an unregistered directory without a record is insufficient evidence.

If branch deletion fails after checkout removal, remove keeps the branch with warning `branch_kept_delete_failed`, `branchKeptReason: "delete_failed"`, and the Git error in the item `detail`. This does not fail the item or stop later targets; branch-only failures exit 0 and have no retry command. Decide on any later branch cleanup with Git.

## Partial completion and retries

A failure after persistent removal exits 6 and retains every item result. Completed removals also remove their records, so repeating the original command may exit 3. Fix the cause, then run `error.details.retryCommand`, also shown as `Retry with` in text. The retry is one invocation: `cd <primary> && rabi -R <primary> remove [flags] -- <unfinished paths>`. It selects only unfinished checkout or record work, preserves permission flags and output mode, and protects selectors with `--`. Run hints in bash or zsh; paths are shell-quoted and control characters use ANSI-C quoting. Metadata cleanup is retried only for recorded targets, using the absolute path spelling saved in the record before removal. Location selectors are fixed before removal. A linked checkout supplying pre-remove hooks is removed last; retries preserve its configuration with `--source-checkout PATH`, which must belong to the selected repository. Once that source is removed, only record cleanup remains and retries disable hooks. Retries add `--no-hooks` when the original command disabled hooks or its source had no pre-remove hooks, preserving hook non-execution even if primary defines hooks. With `-R PRIMARY`, dot also resolves a recorded checkout whose Git registration disappeared.

## Exact squash and rebase evidence

Squash and rebase checks compare complete changed entries: exact paths, file modes, and full before/after blob or gitlink IDs. Evidence comes from non-merge commits on the base's first-parent history. A squash must match one base commit; rebased history must match every workspace commit to a distinct base commit in ancestor-to-tip order. A base commit cannot prove multiple reapplications. Base history remains evidence after later edits. Evidence found only on side histories, unverified merges, ambiguous merge bases, Git failures, and differing file contents keep the branch. These checks do not run external diff or textconv commands, write Git objects, or require `merge-tree --write-tree`.

## Garbage collection

GC operates only on the current or `-R`-selected repository. It defaults to all three criteria: integrated work (`--merged`, including verified squash/rebase history and merged PR evidence), closed or merged linked PRs (`--closed-pr`), and missing directories or registrations (`--orphaned`). `--older-than D` filters by `createdAt`; unknown creation times are excluded and age alone never creates a candidate. D is a positive integer plus `m`, `h`, `d`, or `w`. Without merged PR evidence, a branch still at its creation commit is not merged. Git reflog checks for older and unrecorded checkouts remain conservative.

Without `--apply`, gc returns `plan: true` and exit 0, including protected candidates. Applying follows remove safety rules, skips dirty or unpreserved candidates, and reports a targeted `rabi remove 'NAME' --discard-changes` or `rabi remove 'NAME' --delete-unpreserved-branch` hint. Permissions are never bundled. Hints pin the repository and verify that the selector resolves uniquely. The cd/dot fallback requires an existing directory. For a missing directory, hints use a recorded PR/issue selector when possible; otherwise they show an explicit `git -C REPO worktree remove --force -- PATH` command that discards only that Git registration and its HEAD reflog. Any remaining metadata record can be cleaned by a later orphan gc. Orphan cleanup removes stale records and registrations while preserving branches and any remaining checkout files. Missing gh or unavailable PR status is reported as `unavailable`. Each target is rechecked after hooks; failures after persistent removal exit 6, otherwise 1.

Actions are `wouldRemove`, `removed`, `skipped`, and `failed`. Repeating `gc --apply` is safe; retired workspaces are no longer candidates.

## Orphaned records

Orphaned records have neither a Git worktree registration nor an existing directory. `list` includes them with a trailing `[orphaned]`; the shared JSON workspace object has `orphaned: true` (false for existing entries), with null `branch` and `head`. `path` and `exec` refuse orphaned names; `show` can inspect their records. `remove <name>` removes only the stale record, exits 0, and reports that the workspace was already gone; it runs no hooks and leaves branches alone. Its existing JSON result uses `workspace.orphaned: true` and `branchDeleted: false`. A live workspace matching the same name takes precedence; multiple orphaned records with the same resolved name are refused as ambiguous. Orphaned records do not reserve names for live workspaces. When a live workspace takes the same name, the orphan remains visible in `list`; use `gc --apply` to remove it, since `remove <name>` resolves to the live workspace.

## Plans before removal

From primary, with `feature/auth` already created:

```sh
rabi remove feature/auth --dry-run --json
rabi gc --json
rabi gc --apply --json
```

GC protects the primary checkout, default branch, current workspace, and Git-locked checkouts. There is no ownership or in-use detection, so coordinate with other agents before removing their workspace. Workspaces isolate files and branches, not processes or services.

GC JSON is `data: {plan, items:[…]}`; each item has `workspace`, `reasons`, `action`, and `detail`, and may include `preservationReason`. See [JSON](json.md) and [exit codes](exit-codes.md).

`rabi run` requires the same repository trust as hooks, without prompting. It runs a Codex, Cursor or Claude parent with the shared task agent boundary in the selected linked workspace; the primary checkout is refused. The parent controls its own actions and subagents; rabi does not enforce task progress, check results, publication or completion. Trust is checked before inspecting worktree status, which can execute configured fsmonitor commands. Locks keyed by absolute checkout path prevent concurrent launches across branch changes and remain live while either the launcher or its parent process group survives. SIGINT/SIGTERM and timeout terminate the parent process group and preserve records; local edits and commits are retained. Missing sessions never silently start over. Skills are optional verbatim instructions, with no resolution or validation by rabi. Parents must not push or call GitHub; publication belongs to deterministic rabi task commands outside the agent.

## Doctor findings

`rabi doctor` writes nothing: it only reads GitHub with GET requests and local Git configuration/committed objects. It never fetches, executes hooks, changes merge policy, or blocks other commands. Its findings are advisory and always exit 0. It never prints tokens, push URLs, raw API responses, or subprocess diagnostics. Missing access is not evidence of safe settings.

| Code | Meaning |
| --- | --- |
| `required_checks_not_enforced` | No required-status-checks ruleset rule protects the default branch. Classic branch protection may still enforce checks; it is not inspected. |
| `force_push_allowed` | No non-fast-forward ruleset rule protects the default branch. Classic branch protection is not inspected. |
| `deletion_allowed` | No deletion ruleset rule protects the default branch. Classic branch protection is not inspected. |
| `merge_queue` | A merge queue is enabled; rabi's merge flow does not support it yet. |
| `ruleset_bypass` | The current user may bypass a named active ruleset targeting the default branch. |
| `token_workflow_scope` | Warning: the OAuth token has `workflow` scope, so anything that can push with it can rewrite CI definitions. Info: no scopes header was returned, so fine-grained/app token permissions could not be determined. |
| `default_workflow_permissions` | Repository workflow tokens default to write permissions. |
| `remote_push_ssh` | An SSH push URL is configured for the default branch push remote, selected by `branch.<branch>.pushRemote`, then `remote.pushDefault`, then `branch.<branch>.remote`, then `origin`. The selected name must be a configured remote other than `.`; otherwise `could_not_check` reports that the push remote could not be determined. SSH keys cannot exclude workflow changes; prefer HTTPS with a token without workflow permission. |
| `workflow_review_manually` | Info: a committed workflow file needs manual review of its triggers and permissions; doctor does not parse workflow YAML. |
| `could_not_check` | A named check lacked API access, authentication, a default branch, or readable local data. Its reason is sanitized; no credentials are included. |

Doctor lists `.yml` and `.yaml` entries directly inside `.github/workflows/` on the locally available default-branch tip (remote-tracking tip preferred, local branch fallback), including symlinks and submodule entries with those names. Nested directories and other files are ignored. Only the `.github` and `.github/workflows` trees are read. It emits one informational `workflow_review_manually` finding per file, without reading workflow contents or parsing workflow YAML. Review each file's triggers and permissions manually. No workflow files means no workflow findings; an empty report is not proof of CI safety.

Only rulesets are inspected through `rules/branches`; classic branch protection is not inspected. Rulesets are paginated, including inherited rulesets, and active details are inspected for default-branch conditions and bypass access. Unknown ref pattern forms are conservatively included and cannot establish an exclusion. Doctor inspects the locally available default-branch tip without fetching; rerun after updating refs yourself if current remote workflow definitions are needed.

## Local task bookkeeping

Task records live under `state_dir()/repositories/<common-dir hash>/tasks/`, outside the repository and workspaces, so agents committing workspace files do not include them by accident. Directories use 0700 and files 0600; task writes use an exclusive file lock, atomic record replacement and append-only events. New tasks are published from staging directories only after both files are complete. Tasks and handoff memory share repository identity validation through `repository.json`; an unreadable task reservation blocks creation with an error naming its ID. These records are local bookkeeping claims, not GitHub evidence or an authorization to merge. Local store commands do not launch agents, create workspaces or branches, or push. Local-text creation, list, show and abandon do not call GitHub; external intake uses read-only GitHub evidence. See [task store details](commands.md#local-task-store).

## Task publication

`task publish` requires repository trust and a clean committed task workspace. It reads prechecks from committed objects and refuses changed precheck tables before execution. Checks run with the task agent credential boundary. A failed check, changed HEAD or dirty tree prevents publication; missing tools block as `environment`. Populated submodules and retained submodule data are conservatively refused, avoiding Git recursion through their configuration. Base-policy floors, including the built-in configuration/workflow paths, block as `floor_changed` before any push. A human must inspect and push/approve those changes. A publication lock prevents concurrent abandonment during remote writes.

The recorded base spelling supplies candidate PR base branch names; local refs and symbolic aliases never select the base. Slash shorthand must match exactly one remote branch among its literal and tracking-style interpretations; ambiguous matches fail before task state changes. After verifying the GitHub destination, rabi resolves that branch's tip using hardened `ls-remote`, fetches the exact commit with hardened Git, and verifies common ancestry with the checked HEAD. Fetch negotiation starts from that exact checked HEAD, reusing existing history without importing agent-writable refs. That pinned base commit supplies the base policy and precheck comparison; floors cover its merge-base..HEAD diff. Moving local branches or remote-tracking refs cannot hide protected changes. A missing remote branch, unavailable commit or unverifiable ancestry produces a retryable error without pushing or changing task state.

Agents can write Git metadata. Rabi therefore does not trust repository hooks or configuration for its own publication operations. Network Git runs in temporary isolated Git metadata that uses local objects without loading the source repository's configuration. It passes `-c core.hooksPath=/dev/null -c core.fsmonitor=false -c core.commitGraph=false`, disables credential prompts, strips inherited Git selectors/configuration, and uses only the recorded push URL with `HEAD:refs/heads/<branch>`. Commit-graph reads are also disabled for local inspection through the temporary metadata, so shared `objects/info/commit-graph` files cannot change its ancestry checks. Network Git disables commit-graph writes and automatic GC as well. User credential configuration remains available to rabi; SSH uses GitHub's `git` login in batch mode. No force push is used; an unverifiable or non-ancestor remote tip blocks as `diverged`.

Before any remote inspection or push, rabi independently resolves the task checkout's GitHub repository through `gh repo view`. The recorded push URL must be an HTTPS or Git SSH address identifying that same host, owner and repository; github.com and gh's configured GitHub Enterprise host are supported. Local/file destinations, unsupported transports and proven repository mismatches block as `destination_not_github`, with no push. Failure to resolve the repository, including network or authentication failures and ambiguous defaults, is retryable and leaves task state unchanged. PR writes use the verified explicit repository. Remote edits cannot redirect the recorded push destination, and changes that alter gh's resolved identity conservatively block publication. User Git URL rewrites remain trusted configuration; tests use their own transport-process Git config to rewrite validated GitHub URLs to local bare repositories. The generated draft body contains task intent and commit subjects as quoted data. Before entering `ci`, rabi verifies that the same-repository open PR has the checked head SHA. Interrupted publication may already have changed the remote even if the local record is incomplete. Retry `task publish` in `prechecking` or `publishing`: it checks the remote tip and existing PR before writing again. Publication does not run CI or approve or merge the PR.

These checks limit accidental publication. Shared objects and task records remain local trusted inputs, and same-user processes can still access credential files or race other tools. Coordinate concurrent work and enforce adversarial controls with independent permissions.

## Task advance

`task advance` rechecks the task checkout and fresh PR facts before progressing. It reuses the task implementation boundary and deterministic publication checks, and continues through review, classification, approval waiting, merge preflight and safe cleanup. CI checks must belong to the PR head SHA and match the base policy's check name and app issuer; commit statuses and same-name checks from other apps cannot satisfy them. A stored `ci` state is not evidence of passing checks.

CI job logs are untrusted data. Advance retrieves a bounded tail for failing checks, strips terminal escape sequences and control characters, redacts sensitive environment values and paths, and frames feedback with a random nonce before giving it to the implementer. Log text cannot grant permissions or override the implementer's role restrictions. Prompt framing reduces ambiguity; it does not establish a security boundary against a determined same-user process or malicious provider output. Failed-log retrieval does not turn a failed check into success.

Failure signatures and fix-budget usage are persisted before a fix launch to prevent duplicate automatic launches after interruption. Conflicts return to implementation before waiting for CI. Polling and retries preserve all publication safeguards. Auto-merge is allowed only for tiers explicitly in the policy auto set and without any built-in or policy floor. An empty auto set, missing/failed/invalid/uncertain classification, or a floor requires a maintainer. Floors are recomputed from fresh GitHub PR files against the base-tip policy; a classifier cannot lower them.

Advance writes only pending `rabi/approval` statuses, once per head, with sanitized reasons. It never creates success approval, even outside `RABI_AGENT=1`. A maintainer must supply the latest successful exact-head status from a configured approver. A changed head voids previous approval. Re-derivation requires a clean local descendant of the evaluated/pushed head that matches the PR head; remote-only movement, unpushed local commits and non-descendant local heads block as `record_mismatch` before any implementer launch; changes requested return nonce-framed untrusted feedback to implementation within the shared fix budget. Approval polling expires after `[factory] approval-timeout` (default 24h), returning waiting rather than blocking.

Every advance merge reruns the full preflight with the earned pass bound by its `review_passed` event and record digest, plus a valid classification record. Standalone merge requires the same earned-pass binding unless `--external-review` is supplied; a bare local review record cannot satisfy the review gate. Failures block with the preflight reason, without a retry loop. The merge write uses `--match-head-commit` and the configured method. Remote branch deletion is permitted only by `[merge] delete-branch = true` (default false).

After merge, cleanup uses existing remove checks and trusted pre-remove hooks without force permissions. Only the recorded linked task workspace can be removed; dirty, stashed, unpushed, primary, mismatched or unverifiable checkouts are retained with reasons. Checks run again after hooks. Ignored files follow ordinary remove behavior. Local branches, task history, review and classification records are retained. Cleanup failure does not reverse a verified merge.

## Task reporting

`task report` and `task events` read only the current repository's local task records/events and branch existence. They do not load execution configuration, require trust, acquire locks, create files, launch providers, fetch or call GitHub. They do not repair history or authorize any lifecycle action. Append-before-record replacement means concurrent readers can see a newer event than the record; reports are observations, not transactional snapshots.

Report examples are bounded and passed through the existing diagnostic redactor and terminal-safe display rules. Review fingerprints use normalized body hashes; historical missing evidence remains unknown. Redaction cannot recognize every secret. Event export retains stored event fields, including optional launch diagnostics and user-supplied abandonment reasons; inspect it before sharing. JSON escaping makes event strings data, not terminal instructions.

Batch `task advance --all` uses the same per-task locks, trust, credential boundary, publication checks and merge gates as single advance, and skips blocked/terminal tasks. It anchors execution and cleanup hook selection to the primary checkout, allowing later tasks to proceed if the invoking linked checkout is removed. A failed task does not prevent later tasks from being attempted; cancellation stops further launches. `--all --wait` stops each task at waiting, so one pending CI or approval does not occupy the entire batch. Merged cleanup retries require single-task selection.

## Task approval and merge

`rabi/approval` means a process holding a GitHub token with status write for this repository ran `rabi task approve`, or called the API, for this exact commit. It does not prove a human looked. Any process running as your user, including agents rabi launches, can produce it. It prevents skipped steps. It does not stop a compromised agent.

The `RABI_AGENT` refusal is a tripwire, not a security boundary. Every provider launched by `rabi run` inherits `RABI_AGENT=1`, including resume and `--no-handoff`. Approve refuses any nonempty value, but a process can unset it or call GitHub directly. Protect credentials and repository permissions independently.

Merge uses the policy from the PR base SHA and the same preflight as dry-run, after verifying that its policy content matches the current base-branch tip. The tip is looked up with a GET; changed policy bytes (including addition or removal), an unavailable/invalid tip, or an unreadable tip policy fail the approval item even for auto tiers. Absence at both commits counts as equal. The remaining items are still evaluated, and the tip policy does not replace the PR base policy. An auto tier requires no floor; high is never allowed in `merge.auto`. Otherwise the latest `rabi/approval` status on the exact head must succeed and come from an allowed policy approver. Earlier-head approvals and superseded successes do not count. `--external-review` covers only absent review/classification records and cannot waive approval, failed checks, or other unevaluated items. Agents may execute merge when gates pass.

Local Git state is trusted input, like your credentials. Policy and file kinds are read from local objects when available, and Git also honors local configuration and attribute files (`info/attributes`, `core.attributesFile`). Task reads ignore replace refs and both default and inherited graft files so results stay reproducible, but this is not tamper resistance: a process that can write the repository's Git directory, including agents rabi launches, can change the policy or file kinds the gate reads, just as it can call GitHub directly. When a gate must hold against such a process, enforce it with GitHub repository rules and credentials the process cannot use.

Approval binds to the exact commit, not to a PR or base. The same commit in another same-repository PR into another base carries the same approval status; that merge must still satisfy its target’s policy and preflight.

The write uses `--match-head-commit` to guard against head movement after collection. It does not use `--admin`, `--auto` or `--delete-branch`. Advance may separately delete the remote branch only with `[merge] delete-branch = true`, after verifying its tip still matches the merged head. The deletion push uses the same disposable metadata as publication, ignores repository configuration and disables Git hooks; standalone merge retains branches. Facts are reread even when gh fails; a nonzero result does not prove the remote write had no effect. No automatic write retry occurs. Task status and merge dry-run remain read-only.

## Task agent launch boundary

Every provider launched by `rabi task` or plain `rabi run` uses one shared environment boundary. For run it is applied after repository `[env]` and handoff variables, including first, fresh and resumed sessions, `--no-env` and `--no-handoff`. It removes `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, `SSH_AUTH_SOCK`, `GIT_ASKPASS`, `SSH_ASKPASS`, and inherited `GIT_*` variables, including Git selectors and config overrides. Each launch gets a fresh empty temporary `GH_CONFIG_DIR`, kept alive until process cleanup, plus `RABI_AGENT=1` and `GIT_TERMINAL_PROMPT=0`. Provider authentication remains available. User-configured MCP servers retain their own credentials for Claude and Cursor run parents (Codex parents use `--ignore-user-config`), so this boundary covers inherited gh/Git credentials only.

Child-only `GIT_CONFIG_PARAMETERS` overrides reset `credential.helper` to an empty list, disable `core.askPass` and interactive credentials, and select noninteractive SSH without agent access. Codex retains its default environment secret filtering; these overrides use no variable names containing KEY, SECRET or TOKEN. No user Git configuration is changed. Implementers receive role instructions to edit, check and commit locally, leaving publication to deterministic task commands. Codex implementers and run parents use workspace-write with `sandbox_workspace_write.network_access=false`, `web_search=disabled` and `approval_policy=never`. User configuration and rules are ignored while protected child Git environment overrides are retained. Its deduplicated `--add-dir` grants cover canonical paths outside the workspace for the per-worktree Git directory (normally `worktrees/<id>`) and the common directory's `objects`, `refs` and `logs`, leaving common configuration and hooks outside those grants. Claude uses classifier-guarded `auto` permission mode, denies permission prompts and disallows `Bash(git push:*)`, `Bash(gh:*)`, `WebFetch` and `WebSearch`. Classify retains stricter tool-less flags and an empty cwd. Plain `rabi run` agents can no longer use inherited gh credentials or ordinary Git credential helpers to push. Cursor starts with an empty network allowlist (`{"networkPolicy":{"allow":[]}}`) when `.cursor/sandbox.json` is absent; existing user policies and symlink handling are preserved, and no new host configuration interface is added. Cursor automatic review can still permit execution outside the sandbox; completed requests for it remain audited.

Rabi's Git inspection throughout `task implement`, including workspace discovery and checks before and after launch, uses the stripped boundary environment and command-scoped `core.hooksPath=/dev/null`, `core.fsmonitor=false`, `core.untrackedCache=false` and `core.attributesFile=/dev/null`. Status uses an empty tree as its attribute source and `--ignore-submodules=all`, avoiding checkout filters and recursion into agent-controlled nested repositories. It does not report uncommitted changes inside nested repositories or submodules. Shared task object reads use the same environment protection without requiring temporary directories; committed risk diffs retain their base commit's attributes. Codex run parents reuse the same pre-launch metadata validation and narrow grants; redirected metadata or symlinked grant directories are refused before spawning. The per-worktree Git directory must match its independent registration backlink under the common directory's `worktrees`; redirected checkout pointers and metadata subdirectory symlinks that broaden Codex's write grants are refused. After the provider and its process group stop, rabi revalidates the saved Git directory, common directory, backlink and symlinks using filesystem reads before invoking Git again. Every post-launch worktree Git inspection passes the saved validated paths through `--git-dir`, `--work-tree` and `GIT_COMMON_DIR`, so rewriting the workspace's `.git` file cannot redirect that inspection. The filesystem checks still reject changed `commondir` files before inspection and recheck metadata afterwards. A metadata mismatch exits 4 (`refused`) with `stopReason: "metadata_changed"` and null post-launch Git facts. Inspect and repair Git registration before retrying. Implementers can still change shared objects, refs and reflogs and their own worktree metadata, including `config.worktree` when enabled. Claude's permissions and any broader repository grants may also allow common configuration and hooks to be changed. Humans running Git in other checkouts of this repository may execute agent-written configuration or hooks. Rabi's own publication operations isolate repository configuration and disable hooks, as described above.

These measures stop careless pushes and credential use through the inherited environment and ordinary credential helpers. They do **not** stop a determined agent running as the same Unix user: it can read credential files such as the GitHub CLI hosts file, change its own environment, invoke other clients or use SSH key files. Provider tool restrictions and prompts are defense in depth, not repository access control. Real isolation requires separate credentials or users; that isolation is future work. Use independent repository permissions when the boundary must resist an adversarial process.

## Task reviewer

`task review` and advance's `reviewing` step verify the recorded publication head against fresh same-repository PR facts, then create a fresh rabi-owned detached checkout at that exact SHA. The implementer's writable workspace is never reused for reviewer execution. The base is independently resolved and pinned with the hardened publication transport; records bind head, base and merge-base, and a record for a different head is ignored. Missing remote evidence is retryable; a moved PR head blocks as `diverged` before a stale record can be used.

Reviewers share the task credential boundary. Codex runs `exec --sandbox read-only` with `approval_policy=never`, network access disabled and no `--add-dir` grants. Claude uses `--permission-mode plan` with only Read, Grep and Glob tools; Bash, Edit, Write, NotebookEdit, WebFetch and WebSearch are explicitly disallowed. Claude has no shell access; the diff is supplied in the prompt. Fresh invocations do not resume implementer sessions. Checkout creation disables inherited Git filters and hooks; reviewer Git inspection ignores system and global configuration and disables hooks and fsmonitor. Provider authentication remains available. These restrictions reduce accidental writes; the shared boundary is not access control against a determined same-user process. Reviewers can read files accessible to the same user; before storing findings or posting them to a potentially public PR, rabi redacts known environment secrets, the user's home path, recognizable GitHub tokens, private-key blocks, AWS access keys, and Authorization/token values, but redaction cannot detect every secret.

PR title/body, comments and the full diff are untrusted data inside a randomly generated nonce frame that cannot occur in the supplied content. The fixed instructions require review of deleted, disabled or weakened tests, CI entry points, floor paths, security issues and correctness bugs. Diffs larger than 400 KiB block as `review_diff_too_large` without launching a reviewer. Answers must satisfy the strict nonce-framed JSON contract and match the reviewed SHA; malformed, SHA-mismatched or verdict/findings-inconsistent answers get one retry, then block as `review_invalid`.

Review output is advisory input to rabi's deterministic gates, never an approval. A pass with no important findings permits rabi itself to mark the verified PR ready and upsert one marked comment with a sanitized, bounded summary; it cannot approve, classify or merge. The `review_passed` event binds that pass to its head SHA and record digest. In `ready` or `classifying`, retries reconcile only that record even after base movement, never launch another reviewer, and block as `review_pass_invalid` if the earned pass is missing or invalid. Nits are retained in that summary. Comment edits and duplicate cleanup require both the rabi marker and the authenticated account’s numeric author ID; copied markers on another author’s comments do not authorize mutation. Revisions become framed untrusted implementer feedback and share the fix budget, signature deduplication and repeated-failure stop. Review records are local Git state, trusted like objects and configuration; a process able to edit them and task events can forge their contents. Enforce adversarial controls with independent repository permissions and credentials.

## Task classifier

`task classify` sends the base-commit policy document and full committed diff to one fresh provider session. Providers may incur API costs. The diff is untrusted: a verified random delimiter separates it from the instructions, and the prompt requires escalation for manipulation attempts. This reduces ambiguity, but the classifier can still be persuaded by diff text. Its answer is an assessment, not a security boundary.

Floors and high kind, limit, and unknown-data safeguards are decided before the provider and cannot be lowered by its answer. Path rule/default tiers are ignored by classify. Missing policy documents, oversized diffs, launch failures, timeout, invalid responses, and reported uncertainty escalate to high. The provider runs once in an empty temporary directory. Only tool-less providers are supported, currently Claude with all tools disabled via `--tools ""` and the existing safe flags. Codex is unsupported because its CLI cannot currently guarantee a tool-less invocation without injecting a model catalog; rabi does not inject one. Claude selects its default model unless the base policy supplies `[classifier] model`. Claude safe mode disables custom instructions, memory, skills, plugins, and hooks while preserving provider authentication. GitHub token variables, SSH agent access, and inherited Git selectors/configuration are removed; GitHub CLI configuration is redirected to an empty directory. Provider authentication remains available. The prompt is passed through a temporary stdin file; provider stderr is discarded. Temporary files are removed after completion, and timeout kills and reaps the process group.

Classification records under `<git-common-dir>/rabi/classifications/` are local Git state, trusted like objects, configuration, and the rest of the Git directory. A process able to edit them can forge a verdict. Merge checks the exact PR head, locally computed PR merge-base, and base policy/document blob IDs, never launches a classifier, and never fetches missing objects to validate a record. Missing or stale records remain not evaluated; `--external-review` may waive only the review/classification record items and uses the existing path tier when classification evidence is unavailable. A matching record supplies the effective tier while deterministic safeguards still apply. Enforce adversarial merge controls with independent repository permissions and credentials.

## External task intake

`task new --issue` and `task intake` read issues, collaborator permissions and issue events through GET-only gh APIs; they never comment on, label or close issues. The direct issue author requires current write/maintain/admin permission. Label intake additionally checks the actor who most recently added the requested label, matching label names case-insensitively across all event pages; a later removal, missing actor or non-write actor cannot reuse earlier permission. No matching label event, or a missing or non-user (for example bot) actor, skips with `label_actor_unknown`. It also checks the author through the direct import path. HTTP 404 from a collaborator-permission lookup means no permission for that issue; other unavailable evidence remains an operational failure and never authorizes creation. Unauthorized direct intake refuses as `intake_not_permitted` (4); bulk intake skips it and continues. Issue links are reserved under the creation lock, including terminal tasks, so retries/concurrent intake cannot duplicate tasks. Dry runs write no state.

External title/body text remains untrusted after permission checks. Intake strips terminal escape/control sequences and redacts recognizable secrets and local paths before truncation. Each field keeps its beginning and is capped at 4096 UTF-8 bytes, including a trailing `[truncated]` marker when cut at a character boundary before storage. The implementer prompt includes this intent only inside a fresh collision-checked nonce frame marked as untrusted data; issue text cannot change role restrictions or authorize push/GitHub/network access. Intake never launches agents automatically. The operator creates the linked checkout, runs `task implement`, then explicitly runs `task advance`. Thus agent launches consuming external text follow intake permission checks and still require repository trust and the ordinary task boundary. Framing reduces prompt ambiguity; it cannot isolate a determined same-user process or make issue requirements trustworthy.
